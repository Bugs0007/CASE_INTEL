# Case Intel Case Bot implementation handoff

Prepared 8 November 2026. This is an implementation plan for the current Django and Next.js application. Proposed routes, limits, models, and rollout gates are design decisions for the implementation agent to validate against the current branch.

[Firm collaboration and access control](#5-firm-collaboration-and-access-control) · [Open the local review console](case-bot-review-console.html)

## Product outcome

1. **Dashboard assistant.** Add **Ask about your practice** and an interactive calendar to the dashboard on desktop and mobile. The assistant answers across the signed-in advocate's cases with exact counts, explicit date ranges, and links to the case, hearing, deadline, or appointment behind each answer.
2. **Case drafting.** From an individual case, or after explicitly choosing one from the dashboard, generate a case status memo, a hearing-prep note, or a free-form personal note. Use the advocate's brief, selected material, and verified case records. Offer an editable preview, version history, and source inspection.
3. **Approved output.** Export an approved memo as DOCX or save an approved note to the selected case. Filing, email, calendar mutation, and changes to case facts stay outside the assistant's action allowlist.

The dashboard calendar starts as a compact selectable week with a day agenda and an **Open full calendar** link. The case overview shows exact portfolio totals and a short, paginated list with status, court, and next hearing, plus a link to the full Cases page. Extend the full calendar for any additional views through its existing route. The console is a synthetic prototype of these interactions. It demonstrates the intended flow with fixed records.

## 1. Scope and shared reads

### Conversation scope

- Add a persisted discriminator to Conversation with three values: **case**, **legacy_documents**, and **practice**. Backfill existing rows in a new migration from nullable case ID, with positive fixture coverage for each legacy shape. Preserve primary keys, messages, citations, titles, and exports. Constrain case scope to a case FK and practice/legacy document scope to a null case FK.
- Keep the existing /api/chat/ contract and behavior for legacy callers. Reject a practice conversation ID on the old chat endpoint. Add /api/practice-assistant/chat/ for practice turns. The endpoint sets practice scope itself and obtains owner identity from request.user. Continue a practice conversation only when both owner and scope match. Use a consistent 404 for an inaccessible resource.
- Filter existing conversation listing by its old scope behavior, excluding practice unless a new explicit scope filter is present. Verify the case-panel request with and without case_id and the original all-document listing. Shared detail, messages, export, and deletion may serve practice history after owner validation if their representations support practice references.
- Starting a draft from a practice response creates a new case-scoped draft with a verified case ID and an optional trace link to the practice conversation. A draft never inherits the entire practice chat as context. The server validates the case, source IDs, and optional originating message together. Apply the same case restriction for source selection from a case conversation.

### Practice read model

Implement a reusable owner-scoped service under core/services/practice_assistant/ (proposed). Have both the calendar endpoint and graph nodes call it directly. It accepts typed arguments for date range, kinds, case filters, and pagination. All filtering, counting, ordering, and date arithmetic occur in code or SQL.

| Read | Return and source | Rules |
| --- | --- | --- |
| Portfolio snapshot | Counts by Case.status, active cases with a recorded next hearing, active cases with no scheduled date, paginated case rows with court and status | Define active from existing status semantics with a shared named predicate. Derive next hearing from owned eligible Hearing rows and a documented status mapping. Verify alignment against dashboard and current case cards. Never count two hearings as two cases. |
| Calendar window | Hearing, Task, CaseEvent as tagged entries with record ID, case ID if present, day key, timing/status, safe label, provenance, and source reference | For hearings use aware IST start of day through start of day after the inclusive end. For Task.due_date and CaseEvent.date use plain dates. Exclude dismissed or undated tasks, keep completed dated tasks visible as done, and keep cancelled appointments consistent with the existing calendar's display and marker rules. |
| Open deadline focus | Eligible Task rows with due date, status, needs_review, due_date_basis, and an authorized source order reference when available | Include an unknown or review-required state in summaries where applicable. Use stored due dates and distinguish order directions, manual tasks, and limitation reminders. Keep calculations in the existing deadline service. |
| Selected case facts | Case identity, next hearing, selected recorded tasks, event metadata, and optional retrieved case-document snippets | Resolve the case under owner before querying related models. Apply owner and case checks to both joins and individual records. Supply only fields used for the current answer or draft. |

Start with a 7-day view and a 31-day maximum per calendar request, plus 25 rows per page and a 100 row hard cap for individual query results. Verify bounds and indexes with realistic fixtures. Return deterministic ordering, exact total where counted, pagination, as_of, timezone, and a truncation flag. Keep aggregate counts separate from page length. Handle colliding case names by prompting the user to choose a verified case, with case number and court for disambiguation. Use EXISTS, conditional aggregates, and bounded selects instead of per-case loops. Treat "none recorded" as a statement about Case Intel records. Never infer a court outcome, a date, or an external cause-list result from missing data.

Use a normalized reference object such as:

    {
      "kind": "hearing",
      "id": 18,
      "case_id": 104,
      "label": "Status hearing",
      "recorded_at": "2026-11-09T14:15:00+05:30"
    }

Keep identifiers numeric in the production contract. Construct frontend links from a fixed kind-to-route map. Never render URLs supplied by a model. Existing document citation fields stay compatible. Store typed practice references on the message via a validated versioned field or a related source model. Make history serialization preserve those references. Store document/page citations using existing citation infrastructure where it matches, and keep document revision provenance for draft inputs.

## 3. Draft and note generation

### User contract and entities

The brief includes a verified case, output type, instructions, audience, tone, optional length, and selected sources. Include an optional user-supplied template selection in a later pass after validating its allowed fields and macros policy. Start with a status memo and a personal note. A prep-note template can use known hearing/date data. Start with English; add further languages only after font, content quality, and DOCX validation.

| Entity | Required fields and invariants |
| --- | --- |
| AssistantDraft | Owner, case, kind (document or note), subtype, status, request brief, optional origin conversation/message, current revision pointer, creation timestamps. Use owner and case indexes. Case change starts a new draft. |
| AssistantDraftRevision | Owner, parent draft, monotonic version, structured body, schema version, evidence refs and version/freshness fingerprints, missing required facts, validation warnings, editor provenance, creation timestamp. Immutable after save. Unique draft/version. |
| DraftApproval | Owner, exact revision, actor, approval time, content hash, source freshness marker, action kind. Keep approval tied to one immutable revision. Unique revision and action kind. |
| Draft output | Owner, approved revision, destination, status, file or note reference, safe error, timestamps. Unique revision/destination. Deterministic storage key for an export. |
| CaseNote | Owner, case, title, plain text or structured rich text, origin approval/revision, timestamps. New note rows can coexist with the case's existing notes field. Make later edits user-owned and auditable. |

Reuse OwnedModel and owner-scoped API patterns. Avoid copying full document content into revisions or message history. Store source IDs, version and page metadata, and only necessary approved text. Decide deletions for case, conversation, draft, revision, file, and note explicitly in model tests. Deleting a draft or conversation must not leave accessible orphan exports. Decide whether separately saved notes are retained as owned case records after deleting the originating draft, and show the effect in the UI.

### Graph branch and worker

Use a small drafting graph in core/services/graph/. Reuse existing owner-and-case-scoped retrieval and citation helpers where their contracts fit.

    resolve_case_and_brief
        -> collect_structured_case_facts
        -> retrieve_selected_case_documents
        -> generate_structured_draft
        -> validate_draft
        -> persist_preview_from_worker_result

The graph returns a structured candidate. The worker/application service persists it. Separate context collection from generation so owner checks, evidence assembly, and test fixtures remain deterministic. The selected documents are an additional hard retrieval constraint. For empty selection, use case-scoped retrieval only within the product's consent and context limits, or use verified case records alone when the request does not need documents. Clearly show the included sources in the UI. Never widen to portfolio retrieval during draft generation.

Suggested schema: title, subtype, sections with heading and blocks, evidence IDs per factual block, required verification items, optional warnings, and a generation version. Restrict block types to paragraph, bullet list, and simple table if necessary. Treat advocacy suggestions as suggestions rather than factual assertions. Keep recipient and other user-provided fields visibly marked as user input. Extract and verify legal/case facts against server-provided records. Label unresolved required fields explicitly. If a necessary fact is unavailable, return a reviewable draft with a gap or request clarification. Reject invented identifiers, unsafe markup, unsupported instructions, extra fields, and evidence outside the collected set. Validate structured output against server schema with a bounded repair attempt for providers returning imperfect JSON. Ensure the model can only propose content. Owner, case binding, approval, destinations, permissions, file writes, and job operations remain outside model control.

Use the existing ProcessingJob and process_jobs worker. Add a draft-generation job type with an explicit draft/request relationship, owner, and lane routing. Use a short transaction to create a draft plus queue row atomically when both are in the database. Release locks before calling the provider. Enforce a per-owner pending limit, timeout, context/token cap, and bounded retries. Define claim recovery for interrupted jobs using the queue's existing recovery semantics or a narrowly scoped lease and retry policy. When committing a preview, lock the draft and verify the job claim and expected generation/version. Late or duplicate completions cannot overwrite newer work. Use a fake provider for deterministic tests. Log job metadata, durations, retries and counts. Keep prompts, note bodies, raw order excerpts and client identities out of new logs and trace exporters. Existing chat logs include a query prefix. Review that path before sharing components with sensitive prompts.

### Approval and output

- Preview → edit → submit for review → approve exact revision → save note or export DOCX. User edits create a new immutable revision, with previous approval visible on the old revision only. Required facts, changed evidence, deleted sources, and unresolved verification items must be resolved or explicitly recorded as unknown where policy allows. Treat optional warnings distinctly from blockers.
- Implement approval as an authenticated Django transaction. Lock the draft, check owner, case and latest version, compare the requested revision and current expected version, revalidate required evidence, and store actor/time/hash. Return 409 when the preview is stale or source data has materially changed. Never approve by interpreting model text or a chat message. Preview and approval survive refresh and worker restarts.
- First release uses Django persistence for pending review. The initial graph finishes when its candidate validates, and approval is a separate user request. This keeps the existing LangGraph dependency and avoids introducing checkpoints just to wait on an approval. If a later workflow genuinely needs in-graph pause/resume, verify a compatible persistent checkpointer against the pinned stack, derive an opaque server-owned thread ID per owner and draft, test restart and replay, and keep side effects outside the interrupted node or idempotent. LangGraph resumes an interrupted node from its beginning. [LangGraph interrupts](https://docs.langchain.com/oss/python/langgraph/interrupts) · [Durable execution](https://docs.langchain.com/oss/python/langgraph/durable-execution) · [Persistence](https://docs.langchain.com/oss/python/langgraph/persistence)
- Render DOCX deterministically with python-docx from the approved schema. Use controlled styles, page breaks, case metadata, sanitized filenames, and draft/provenance labeling as appropriate. Test actual paragraphs, tables, page citations, headers, and Unicode. Keep preview editable through the approved revision flow. Reuse private Django storage patterns and authenticated downloads. Reserve an output row by approved revision and destination, then write storage under a stable revision-specific key with checksum. Use retry-safe state transitions and cleanup of abandoned files on partial failure. Download returns only ready outputs after rechecking ownership.
- Store a personal note in the new owner-scoped CaseNote using the exact approved revision. Use an atomic save and a unique revision link to handle repeat clicks. Show it under case detail Notes. Keep generated documents available in draft history. If a later release adds **Attach to case documents**, make it an explicit action and preserve generated provenance. Decide whether generated attachments should enter retrieval, because unreviewed or generated text must never silently become evidence for subsequent drafts.

### Proposed draft API

Use positive integer IDs or opaque UUIDs consistently with existing conventions. Every mutation checks authentication, owner, case, state, expected version, and allowed action. Creation/revision/output actions use an idempotency key scoped to owner and operation. A reused key with a different payload returns 409.

| Method and route | Result |
| --- | --- |
| POST /api/case-assistant/drafts/ | Validate case and brief, enqueue generation, return 202 plus draft and job state. |
| GET /api/case-assistant/drafts/{id}/ | Owner-scoped status, current preview, validation, source links, approved revision, and available outputs. |
| POST /api/case-assistant/drafts/{id}/revisions/ | Persist edited content under expected_revision. Revalidate with the same schema. Return 201 or 409. |
| POST /api/case-assistant/drafts/{id}/approve/ | Approve exact revision ID, requiring the current revision and evidence state. Repeat of the same action returns the existing approval. |
| POST /api/case-assistant/drafts/{id}/outputs/ | Request DOCX or note save for exact approved revision. Return an existing result on replay, or 202 for queued export. |
| GET /api/case-assistant/outputs/{id}/download/ | Owner-checked binary response for ready DOCX. Return an owner-scoped note reference from note outputs. |
| POST /api/case-assistant/drafts/{id}/retry/ | Retry a recoverable failure under the same draft and validated case. Return active job instead of duplicating it. |

For concurrent edits, use expected revision in API requests, database uniqueness constraints, and transactional row locks. Handle stale edit, missing source, no provider, rate limit, worker timeout, cancellation, invalid draft, and storage failure with actionable messages. Avoid a network round trip for every keystroke. Use a clearly labeled save/submit action and a leaving-page warning only while there are unsaved edits.

## 5. Firm collaboration and access control

Sections 1 to 4 establish the personal assistant and drafting flow. Firm membership, shared case access, discussion, and documents can ship independently of firm Case Bot. Firm assistant integration follows only after the case and file policy passes the firm release gates.

### Product model

An advocate uses one account and switches between **Personal** and each firm they belong to. Personal opens the existing dashboard and case list. A firm opens its own dashboard, calendar, Cases, and Documents, with **My assigned cases** and **All firm cases** views. A firm may include thousands of cases. Default to My assigned cases for daily work and load a paginated directory for browsing. Label the scope in the header, on new-record forms, and in exports. Never infer scope from a remembered case number, an AI response, or the last firm visited.

A firm has one canonical record per tracked matter. All participants reference the same case, hearings, orders, tasks, calendar events, and documents. **Work on this case** creates a relationship with the advocate's firm membership. It does not duplicate a case or transfer anything to Personal. A member who belongs to two firms sees separate firm directories and assignments. The same external court case can have separate records in Personal and each firm, with independent files and work. The first release starts with new firm cases. Defer any personal-to-firm transfer until there is a reviewed, selective disclosure and migration flow.

Use the group model for membership and the case model for work. Firm admins manage who belongs to the firm, and each case has its own roster and discussion. Start with one asynchronous case discussion for coordination. Put deadlines, decisions that need a durable record, and document changes in their respective case surfaces so a message does not become the only record of an obligation.

### Permission model

Use two firm roles and one case role. **Firm admin** manages membership and ordinary-case assignments. **Firm member** can browse ordinary cases. **Case steward** is an assignment role that manages an individual case and, for a restricted case, its authorized roster. An ordinary **assigned advocate** can contribute to a case. Resolve every action from active firm membership, case visibility, active assignment, and action. Use verified relationships to determine access. An admin role is not a content override for restricted matters.

| Action | Firm admin without a case assignment | Active unassigned member | Assigned advocate | Case steward |
| --- | --- | --- | --- | --- |
| Browse ordinary case, documents, calendar and discussion | Read | Read | Read | Read |
| Browse restricted case content, files, search results, calendar and discussion | No | No | Yes, with explicit active grant | Yes |
| Join My assigned cases | Ordinary open case when self-assignment is enabled | Same | Already assigned | Already assigned |
| Edit case working fields, tasks, hearing notes, and shared appointments | Assign self on ordinary case first | Join ordinary case first | Yes, for the assigned case | Yes |
| Upload a file or create a new revision | Assign self on ordinary case first | Join ordinary case first | Yes, for the assigned case | Yes |
| Post in case discussion and mention eligible participants | Assign self on ordinary case first | Join ordinary case first | Yes, for the assigned case | Yes |
| Edit or withdraw an own discussion post | Only with active contribution rights | No | Own posts within retention policy | Own posts within retention policy |
| Manage ordinary roster | Yes | No | Leave own assignment when permitted | Yes, for the case |
| Grant or remove restricted case access | Only as a steward on that case | No | Leave own assignment when permitted | Yes, for the case |
| Create a firm case, invite, remove, and change firm roles | Yes | No | Only with admin role | Only with admin role |
| Change case visibility | Only with the case steward role | No | No | Yes, with the confirmation and audit rules below |
| Archive a case | Ordinary cases only | No | No | Yes, within case policy |
| Archive or restore a file, or redact another person's post | Only with the case steward role | No | No | Yes, within case policy |
| Approve or publish a shared draft | Only with active case assignment and assigned publish permission | No | Review own draft. Shared publishing by steward in the first release | Yes, with exact-revision approval |

An admin who also has a case assignment combines those rights. The admin assignment board shows advocate, role, and case for ordinary matters. For a restricted matter, show an opaque assignment reference and assignee only if the firm's confidentiality policy permits administrative roster visibility. Default to showing restricted rosters to authorized stewards only in the pilot. A screened admin cannot reveal restricted case existence through search, counts, empty states, exports, assignment badges, notifications, or fabricated IDs. Use a separate aggregate for visible cases and label it accordingly. Select the firm's restricted-roster policy before onboarding sensitive matters.

Stewards can restrict an ordinary case only after previewing which current assignments retain access. Lock the case, confirm an active steward remains, revoke anyone outside the intended roster, and bump the access epoch in the same transaction. Only an authorized steward can propose widening a restricted case. Require explicit steward confirmation and audit it. Keep firm admins from creating their own restricted grant by changing visibility or assigning themselves. Firm admins may view ordinary assignment coverage without taking write access. Define an audited recovery procedure for an orphaned restricted case before rollout.

### Canonical schema and invariants

| Record | Representation and indexing |
| --- | --- |
| Firm | ID, slug/display name, status, firm settings, access epoch, timestamps. Keep separate from an advocate profile or personal account. |
| FirmMembership | Unique (firm_id, user_id), role admin/member, state active/suspended/removed, epoch, joined_at, revoked_at, changed_by. Index (user_id, state) for workspace picker and (firm_id, state, role) for roster and last-admin checks. Retain inactive membership for audit. |
| FirmInvitation | Firm, normalized target email, token digest, expiry, consumed/revoked timestamps, invited_by, optional membership link. Firm has no personal owner. Add created_by separately from authorization. Index firm/status/sort for catalog. Add firm-scoped unique normalized CNR where present. For a case without CNR, derive and review a court-qualified identifier rather than forcing global case number uniqueness or auto-merging ambiguous records. |

This is an explicit exception to the existing OwnedModel contract for migrated, firm-enabled records. Document the new invariant and keep the old owner-required behavior on unrelated models. Deploy schema changes additively. Audit model managers, list/detail/search, writable serializer relations, signals, admin, exports, system jobs, and ORM queries before allowing owner-null firm rows. In particular, an old filter that takes case.owner_id could match rows from unrelated firms if the value is null. Keep existing personal case IDs and owner uniqueness. Allow firm writes only through scope-aware services, and fail closed for unsupported child types. Use database constraints for ownership integrity and consider row-level security as defense in depth after testing transaction/pooling and worker roles. The Django policy remains the primary access decision. ### Membership lifecycle and route contract

- **Create a firm.** During the pilot, allow creation through an explicit provisioning action for an eligible signed-in advocate. Create the firm and its first active admin membership atomically, with a unique slug and an idempotency key. An account can join multiple firms. Each admin role is local to its own firm.
- **Invite.** An authorized admin invites a normalized email. Default to member and promote separately. Send a single-use, cryptographically random token via the invite channel. Store only its digest. Accept after authentication and proof of the verified address. The current platform signup token's email only prefills signup. Google authentication checks a verified email claim. Add explicit verification for any other account path before permitting firm acceptance, and keep firm invitations separate from [platform signup tokens](../core/models/invite_token.py). Under one transaction, lock the firm and invite, check expiry, inviter permission and state, create or reactivate the membership, and consume the token. A same-user replay can report already redeemed, with no new grants. Mismatched identity, expired token, and unauthorized replays are denied. Rate-limit issuance and redemption and avoid exposing whether an account exists.
- **Assign.** An admin or steward can assign eligible active members within its scope. For an ordinary open case, the optional self-assignment setting defaults on and uses a clear **Work on this case** confirmation and audit event. A firm can turn this off and use roster assignment. Unassign removes the worklist entry and write ability. On a restricted case it also removes case read access. Reject any operation that would leave a live restricted matter without a steward.
- **Remove.** Lock the firm to serialize role changes and prevent removing/demoting the last active admin. Normal removal of the sole restricted steward requires handoff. Define an audited emergency suspension that immediately revokes an unsafe account and places any orphaned restricted case into controlled recovery, without handing content to a screened admin. Mark the membership removed or suspended and advance its epoch, revoke active assignments and pending grants for that membership, and log the event atomically. The firm keeps shared records, and historical attribution remains. Reinviting the same user starts a new membership epoch with no recovered case grants. A removed member retains their personal login and personal case access. Review active session handling, file leases, job results, and cached data as part of revocation.
- **Request policy.** Use explicit /api/firms/{firm_id}/... endpoints. Resolve firm membership server-side from the authenticated user. Use scoped query builders for case list/detail/related reads and writes. Never trust owner, firm, case, role, or membership epoch from a request body. Compare any child route and foreign key under the same verified scope. Use a 404 for inaccessible firm/case IDs, a 403 for a visible resource with a disallowed action, and 409 for a stale revision or last-admin/steward constraint. Invite acceptance is a distinct endpoint guarded by token and verified identity.
- **Client state.** Mount firm routes under /firms/[firmId]/. Keep personal URLs and feature flags. Give queries firm ID, actor/session and applicable visibility generation. Cancel old-scope requests and clear relevant caches on scope switch, sign-out and revoke. Discard late responses. Keep only selection state in local storage. Use private/no-store for sensitive files and results. A refresh, service worker, export or deep link must pass authorization again. Assignment views use joins, not personal record copies.

Initial firm endpoints include GET /api/firms/, member and invitation management, GET /api/firms/{firm}/cases/?view=assigned|all, case detail, a roster endpoint, explicit self-assignment, and case-scoped discussion and document endpoints. Use cursor pagination for case and discussion lists. Derive capability flags from policy for UX, but enforce the same action server-side. Include action-specific denial tests. Counts and filters operate on the authorized set before grouping. Invitations, assignments, posts, uploads and notification delivery should be retry-safe under a scoped idempotency key.

### Case discussion and shared work

- Add one discussion per case through a case FK, with one row per actual post. Store author membership, body, created_at, edited_at, state and reply_to when needed. Use safe plain text or a narrowly allowed rich-text schema. Verify reply and mention membership belongs to the case's allowed audience. Keep a typed document-version link instead of storing a second attachment blob. Verify access to a linked object at both post and read time. Keep conversations and external client messages separate.
- Use cursor pagination by immutable created_at and ID with a case index. Store a sparse CaseReadState only after a user opens a discussion. A unique (case, membership) row with monotonic last-read cursor is sufficient. Compute unread from visible posts, never create one unread row per message per member. Give participants edit and delete of their own posts according to firm retention policy, and permit steward redaction with audit rather than impersonation.
- Start with an in-app case activity timeline and visible-tab polling. Add mention notifications through a transactional outbox and dedup per event and recipient. Recheck current access, mute/preference and eligibility before delivery and before rendering previews. Avoid names, text, or private case data in notification subjects for restricted cases. Keep DMs, presence and real-time infrastructure outside the first release. Use the existing PostgreSQL job infrastructure where a delivery worker is needed.
- Make tasks, approvals and case calendar records explicit actions. A discussion post alone cannot update case facts, create a deadline, send an email, or approve a draft. Give messages stable links to the corresponding task, order or file when they exist. Discuss retention, exports, and moderation with pilot admins before enabling sharing.

### Documents and server usage

**Listing UX.** Use a firm Documents view and a per-case library with the same server-side filters. Show logical documents by newest activity or stable name, grouped or filtered by Orders, Uploads, Generated, and processing state. Show title, case if in the firm-wide view, source, last updated, uploader, status, and version count. Pin or surface the latest verified order where useful. Collapse revisions into an expandable history. Show a preview or signed access only when opened, lazy-load thumbnails for visible rows, and keep the full filtered list paginated with a stable cursor and accessible loading/error/empty states. Display archived and processing failures explicitly. Prefer search over scrolling. Use familiar controls on mobile and keep destructive actions separate from download.

**Listing queries.** Build a firm-only compact serializer with selected fields. Do not return file paths, extracted text, raw worker errors or object URLs in list results. Limit first page to a starting 25 or 50 rows, enforce a hard cap, and use stable cursor keys such as (updated_at, id). Apply scope and case ACL before filters, totals or facets. Fetch latest processing state via a bounded indexed subquery or maintained pointer instead of prefetching every job. Measure query count, rows scanned, payload size and latency with pilot-sized fixtures. Add firm/case/date indexes after checking query plans and keep title search within the authorized set. Reuse this compact read path for personal only after a separate parity check.

**Storage and indexing.**

1. Keep one logical Document per intentional item and immutable DocumentVersion rows for actual revisions. Store one canonical current version pointer and enforce unique version numbers per document. Author, uploader, file provenance and policy are independent of bytes. Same case upload retries use idempotency, not another Document row. Personal files keep their existing paths and behavior during the initial rollout.
2. Store binary content in private object storage with opaque firm-prefixed keys, size, hash, media type and version metadata in the DB. Accept direct-to-storage uploads only via a narrowly scoped short-lived upload grant. Bind it to firm, case, member epoch, content constraints and a pending upload ID. Verify size, checksum and actual content, quarantine until scan/validation, and finalize idempotently after rechecking permission. Reject overwrites, mismatched keys, unsafe files and abandoned upload IDs. Expire orphan objects via a grace-period reconciler. Record a separate upload session and file version from the initial request. Large files should not be buffered in application memory.
3. First optimize listing and processing. Then measure duplicate bytes, repeated OCR/embedding, and storage costs. If material, introduce an immutable DocumentBlob with unique (firm_id, verified_sha256), and let authorized versions reference it. Use one blob only within the same firm, with no cross-firm or personal lookup. Confirm a caller cannot probe a restricted matter via dedup response shape, timing, quota, or accessible IDs. Use transactional references, retention/legal-hold checks and grace-period garbage collection for unreferenced blobs. Reuse OCR/extraction within the firm only behind authorized version references. Before search ranking, filter document/version associations to cases visible to the actor. Keep retrieval provenance attached to the version that grants access.
4. Check permission on every download, inline preview, range request, version and export. Start with an authenticated streaming or edge-gated route for firm files when immediate denial of future requests is required. Private short-lived presigned GETs are a possible performance mode only if pilot admins accept the remaining exposure until expiry. A URL already issued can be used until it expires, and bytes already downloaded cannot be recalled. Do not reuse the personal media fallback or long-lived signed URLs for firm files. Avoid putting object paths, auth tokens and URLs in logs. [AWS presigned URL behavior](https://docs.aws.amazon.com/AmazonS3/latest/userguide/using-presigned-url.html)
5. Queue indexing on canonical version ID and firm/case, keyed by version and job type. Separate a user-initiated job from a system maintenance job. Recheck the initiating actor and case access before executing and committing user jobs. A system job runs as a narrowly scoped service against an active firm case. Use locks/idempotency for retries and finalize once. Apply access invalidation to previews, file responses and search indexes on archive, restriction, or removal.

### Calendar, automation, and Case Bot integration

- **Calendar.** Store one hearing, task, or appointment for the firm case. Derive a personal work view from assignments rather than copying calendar rows. The firm dashboard calendar has My assigned and visible firm-case filters, plus an explicit share choice when creating a firm appointment. Personal appointments remain private. Use the same IST date semantics described in section 1. Read only authorized items for both list and day markers. Keep counts, suggestions and links scoped to the selected workspace.
- **Tracking and alerts.** Run court sync and order ingestion once per canonical case. Separate public lookup cache keys from private case and job scope. Replace owner-based task and refresh dedup with firm/case-aware keys for firm records. For member-specific reminders, add a recipient dimension to uniqueness, and resolve current membership, case visibility, assignment and preferences again at delivery. The same case record can inform several recipients without storing several hearings.
- **Assistant.** Implement personal and firm assistants as explicit scopes. Add firm portfolio retrieval only after case permissions, file access, and redaction tests pass. Give both keyword and vector retrieval an authorized version/case set before ranking. Verify citations and all case IDs supplied to synthesis, including uncited input. Record those dependencies on a turn so a revoked case invalidates the answer and its export. Do not fold discussions into retrieval by default. Keep case-private working drafts and histories within the firm and actor scope. Exclude firm-derived content from personal history, search, calendar and exports even if the user authored it. Revalidate access at draft generation, approval, publishing and download. Share a note or file with the firm only via an explicit steward-approved action.
- **Billing and integrations.** Keep personal fee, invoice numbering, email, and client updates on their current routes. Plan firm billing and delegated access as a later feature with its own permissions, audit, numbering, and consent. Preserve portal and provider configurations for personal users. Firm administrators need an explicit decision on use of a third-party model with firm documents before enabling drafting.

Include anonymous, no membership, removed membership, pending invite, same user in different scopes, ordinary unassigned, ordinary assigned, restricted assigned, restricted steward, admin with and without a grant, and system worker. **Product decisions to confirm for the pilot.** Ordinary cases are firm-visible. Case assignment enables contribution. Self-assignment is available on open ordinary cases unless the firm disables it. Restricted roster administration defaults to its stewards. New firm cases start in the firm and there is no automatic transfer of personal matters. Communication starts as a per-case discussion. Firm bills and bulk personal imports are separate decisions. These defaults are deliberate so the team can test a coherent access model before widening it.
