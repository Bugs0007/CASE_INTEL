# Case Intel

Legal case management platform for a solo/small-firm advocate practicing in Indian courts: case tracking (including live eCourts integration), document management with AI-generated order summaries, a general-purpose AI chat over uploaded case documents, hearing/cause-list tracking, advocate search, appearance-fee invoicing, and travel booking.

## Stack

- **Backend:** Django 5.1.11 (pinned — see Gotchas) + Django REST Framework 3.17, `core` is the only app
- **DB:** PostgreSQL with `pgvector` (RDS in production)
- **AI — two separate, unrelated pipelines, do not conflate them:**
  1. **"Case Bot" chat** (`core/services/graph/`, `core/services/ai_workflow.py`, `ChatView`) — a general-purpose RAG chat over a case's uploaded documents, live in the frontend as the "Case Bot" panel on the case detail page. LangGraph 0.6.11, lean 3-node pipeline (`hyde_expand → hybrid_search → generate_answer`), backed by `DocumentChunk` embeddings + `VectorSearchService` hybrid (pgvector cosine + tsvector keyword, RRF fusion, cross-encoder rerank). Persists `Conversation`/`Message`/`Citation`.
  2. **Order-summary** (`core/services/order_summary/`) — a single-order-PDF summarizer. Does **not** use LangGraph, the graph pipeline, or vector search at all: it reads `Document.extracted_text` directly, classifies the order (`routing.py`) to skip the LLM entirely for unreadable/routine/short orders, and calls `get_llm_client()` directly for a one-shot JSON summary (`prompt.py`, `service.py`). Runs exactly once per order, from the `process_jobs` worker after the order's document finishes processing — never from a view or serializer.
  - LLM (chat generation) provider is independently configurable — Groq, Ollama, or OpenAI — and is shared by **both** AI paths above via `get_llm_client()`.
  - Embedding provider is independently configurable too — Gemini (`gemini-embedding-001`, truncated to 768-dim via `output_dimensionality`), Ollama (`nomic-embed-text`, native 768-dim), or OpenAI as a fallback path. Only the chat path's ingestion pipeline (`document_processor.py`) uses embeddings; order-summary does not.
- **Court data:** `bharat-courts` wrapping the live `services.ecourts.gov.in` (District Courts) / `hcservices.ecourts.gov.in` (High Courts) portals for case tracking, order downloads, and advocate search. First-party fixes for portal bugs bharat-courts doesn't handle — see Gotchas.
- **Cause lists:** Telangana High Court only, PDF-based (not HTML scraping) — see Gotchas.
- **Frontend:** `frontend-next/` — Next.js 15 / React 19 / TypeScript / Tailwind, deployed on Vercel
- **Background jobs:** a `ProcessingJob` row per unit of work (`document`, `order_sync`, `advocate_import`, `advocate_search`), claimed by the `process_jobs` worker via `select_for_update(skip_locked=True)` — **deliberately no Celery/Redis**, Postgres is the queue. See Gotchas.
- **Config:** `python-decouple`, all environment-dependent settings must be read via `config(...)` in `case_intel_project/settings.py` — never hardcode `DEBUG`, `ALLOWED_HOSTS`, `SECRET_KEY`, DB credentials, or API keys directly in source.

## Architecture

- **Models** (`core/models/`, 26 total, all registered in `core/admin.py`) — grouped by domain:
  - Case/contacts: `Case`, `ClientContact`, `CaseTag`/`CaseTagMap`, `Hearing`
  - Documents: `Document`, `DocumentVersion`, `DocumentChunk`, `DocumentTag`/`DocumentTagMap`, `Folder`
  - Case Bot chat: `Conversation`, `Message`, `Citation`
  - Court tracking/orders: `CourtFetchLog`, `CourtOrder`, `CourtTrackingPreview`, `AdvocateSearchPreference`
  - Billing/travel: `AdvocateProfile`, `AppearanceFee`, `TravelBooking`
  - Email: `Email`, `EmailAttachment`, `GmailCredential`
  - Jobs/misc: `ProcessingJob`, `ActivityLog`, `Task`

  All case-data-holding models inherit an `OwnedModel` abstract mixin (`owner` FK to `User`, `on_delete=PROTECT`) for multi-tenant row isolation — see Conventions below.

- **AI service factory** — `core/services/ai_service_factory.py` has two independent toggle chains, one per axis. `get_llm_client()` checks `USE_GROQ` first (routes to `LLMClient` with Groq's OpenAI-compatible `base_url`), then `USE_OLLAMA` (`OllamaLLMClient`), then falls back to OpenAI (`LLMClient` with no `base_url` override) — untouched by `USE_GEMINI_EMBEDDINGS`. `get_embedding_service()` checks `USE_GEMINI_EMBEDDINGS` first (`GeminiEmbeddingService`), then `USE_OLLAMA` (`OllamaEmbeddingService`), then falls back to OpenAI's `EmbeddingService` — untouched by `USE_GROQ`. `GeminiEmbeddingService` always passes `output_dimensionality=settings.EMBEDDING_DIMENSIONS` (768) explicitly on every `embed_content` call and batches up to 100 texts per request (the API's per-request cap); it raises on any API error rather than falling back to another provider mid-document, since mixing embedding models within a document corrupts retrieval.
- **Document ingestion** (`core/services/document_processor.py`) — extract text (PyPDF2/python-docx/plain read) → OCR if scanned (`ocrmypdf`) → spaCy sentence-aware chunking → embed in batches of 100 → bulk-insert `DocumentChunk` rows → populate `tsvector` for keyword search. SHA-256 content-hash dedup: an identical file re-upload clones the original's chunks instead of re-embedding. This pipeline feeds **only** Case Bot retrieval; order-summary reads `Document.extracted_text` directly and never touches `DocumentChunk`.
- **eCourts integration** (`core/services/court_data/`) — `CourtDataProvider` abstraction (`base.py`) over `EcourtsProvider` (`ecourts_provider.py`, the only module that imports `bharat_courts`), with the HTML/PDF response-parsing functions split into a sibling `ecourts_parsing.py`. Public methods are synchronous; `asyncio.run()` bridges into bharat-courts' async client internally. `court_tracking.py` orchestrates the case-detail-page-facing setup/preview/confirm/refresh flow (rate-limited to one real fetch per case per hour); `court_order_sync.py` downloads order/judgment PDFs for a tracked case into the normal document pipeline (sequential, capped per sync, deduped by `CourtOrder.dedup_key`).
- **Order summaries** (`core/services/order_summary/`) — see AI section above. `routing.py` classifies order text (unreadable / too-short / routine-adjournment / needs-LLM) via a two-sided marker system: a "substantive" marker (e.g. "is directed", "shall file", "stayed") always overrides a length-based free path, since a short order can still carry a real direction.
- **Advocate search** (`core/services/advocate_search.py`) — a state-wide **fan-out**: the eCourts "Search by Advocate" form is scoped to one court complex at a time, so this runs the search sequentially across every district/complex in a state (dozens to hundreds of CAPTCHA-gated portal calls, ~10–45 minutes depending on state size), aggregating and deduping results by CNR. Runs only inside the `process_jobs` worker, never inline. Per-district and per-complex failure isolation (one bad complex doesn't abort the run); progress and partial results are persisted to `job.payload` incrementally after every district so a crashed worker doesn't lose completed work, and a separate "retry failed districts" job can re-run just the gaps. **Concurrency cap:** only one `advocate_search` and, separately, only one `advocate_import` job may be in flight system-wide at a time (`JobAlreadyRunningError`) — running two fan-outs at once against the portal caused a production outage.
- **Cause lists** (`core/services/cause_list/`) — Telangana High Court only. Not a plain HTML scrape: the portal requires a CAPTCHA-gated POST returning a meta-table of per-bench PDF links, and the actual list is a **PDF**, parsed with `pdfminer.six` using per-character **coordinates** (not text order) — the S.No. column has to be paired with the case-number column by vertical position, and column x-offsets are detected per document rather than hardcoded, since the real lists use at least three different layouts. No scheduler triggers this automatically (no Celery, and deploy carries no cron entry) — `manage.py fetch_cause_lists` is meant to be run by two cron lines the operator adds themselves (see Common commands).
- **Invoicing** (`core/services/invoice_service.py`) — `AppearanceFee` lifecycle is `PENDING → INVOICED → PAID`, enforced by this module (views never assign `fee.status` directly). Per-advocate invoice numbering via `select_for_update()` on `AdvocateProfile` so concurrent generates from the same advocate serialize correctly. PDF rendering via `fpdf2` (pure Python, no system deps, unlike WeasyPrint). Email delivery is optional — see `INVOICE_EMAIL_CONFIGURED` in Gotchas.
- **Background processing** — `ProcessingJob.job_type` is one of `document`, `order_sync`, `advocate_import`, `advocate_search`; the `manage.py process_jobs` worker (systemd unit `case-intel-worker` in production, see `deploy/case-intel-worker.service`) claims jobs via `select_for_update(skip_locked=True)`. `updated_at` doubles as a heartbeat — a `running` job whose heartbeat has gone stale is reclaimed (crashed-worker recovery). Scanned PDFs (negligible extractable text) are OCRed with `ocrmypdf --skip-text` in 10-page batches inside the worker (`core/services/ocr_service.py`), setting `Document.ocr_applied`.
- **Views/serializers** — `core/views/`, `core/serializers/`, both modular packages split by domain (case, hearing, document, chat, conversation, folder, gmail, email, court_order, case_tracking, advocate_search, advocate_profile, appearance_fee, travel_booking, client_contact, auth, dashboard).
- **URLs** — `core/urls.py`, all endpoints mounted under `/api/`.
- **Multi-tenancy** — `core/views/mixins.py`'s `OwnerScopedMixin` is applied to every generic view; it filters `get_queryset()` by `request.user` and stamps `owner` on create, which also covers object-level retrieve/update/delete since DRF's `get_object()` reuses `get_queryset()`. Plain `APIView`s (dashboard, chat, gmail, case_tracking, advocate_search, appearance_fee, travel_booking, document upload/process/download) are scoped manually — check each one individually rather than assuming the mixin covers it. Serializers with writable FKs to owned objects (`Hearing.case`, `Document.folder`, `Folder.parent_folder`) scope those PK querysets to the caller's own rows too.
- **Auth** — DRF `TokenAuthentication`. Frontend sends `Authorization: Token <token>`, stored in `localStorage`. Chosen over session/JWT because Vercel↔EC2 is cross-origin with `CORS_ALLOW_CREDENTIALS=False`, so cookies don't work here regardless.

## Workflow conventions for AI-assisted changes (Claude Code)

- **Never run `git commit` or `git push`.** Leave changes uncommitted in the working tree for manual review and commit.
- **Never touch deployment configs**: systemd units, nginx conf, GitHub Actions, `.env` files. Flag needed changes in your summary instead.
- **Every model holding user/case data must have an `owner` FK** (via `OwnedModel`) and **every queryset must filter by `request.user`** — either through `OwnerScopedMixin` or manual scoping on plain `APIView`s. Check writable serializer FKs too (see Multi-tenancy above) — an unscoped PK field is an IDOR path even if the view itself is scoped.
- **Migrations**: never edit an applied migration; always `makemigrations` fresh. For migrations adding a NOT NULL column to a table with real production rows, use the `CHECK ... NOT VALID → VALIDATE → SET NOT NULL` pattern and `CREATE INDEX CONCURRENTLY` rather than a bare apply, to avoid an `ACCESS EXCLUSIVE` lock on RDS during business hours.
- **Django is pinned to 5.1.11 — do not upgrade it** (see Gotchas) as part of unrelated work; if a task seems to require a newer Django, stop and flag it rather than bumping the pin.
- **The Case Bot chat pipeline and the order-summary pipeline are separate systems that happen to share an LLM client factory.** Don't assume a change to one affects the other, and don't route order-summary work through LangGraph (or vice versa) without a deliberate decision to merge them — they were built independently and currently have no shared code path beyond `get_llm_client()`.

## Gotchas

- **Django is pinned to 5.1.11** — do not upgrade. A newer Django version conflicts with dependencies as installed here. Check `requirements.txt` compatibility before ever touching this pin.
- **`DEBUG` / `ALLOWED_HOSTS` / `SECRET_KEY` must come from `.env` via `python-decouple`**, not be hardcoded. (`SECRET_KEY` was hardcoded in source until this was fixed — if you see a hardcoded fallback default in `settings.py`, that's intentional for local-dev-without-`.env` convenience, not a place to put real secrets.)
- **Embedding dimensions are NOT fully dynamic.** `settings.py` computes `EMBEDDING_DIMENSIONS` dynamically based on `USE_GEMINI_EMBEDDINGS` / `USE_OLLAMA` + the configured model (768 hardcoded for Gemini regardless of `GEMINI_EMBEDDING_MODEL`'s native dimension, 768 for Ollama `nomic-embed-text`, 1536 for OpenAI `text-embedding-3-small`), but `core/models/document_chunk.py`'s `DocumentChunk.embedding` field is **hardcoded** to `VectorField(dimensions=768)`. If you switch to OpenAI's embedder (1536-dim, no `output_dimensionality` truncation applied), embedding writes will fail or silently mismatch against the fixed 768-dim column/HNSW index. A real migration (changing the field + re-embedding existing chunks) is required to actually switch to a non-768 provider in a running deployment — flipping the env var alone is not sufficient. Gemini and Ollama are both safe to switch between since both are pinned to 768 already.
- **No Celery, no Redis — Postgres is the only queue, and this is deliberate, not a TODO.** Verified: zero `.delay(`/`.apply_async(`/`@shared_task` calls anywhere in the codebase. `django_celery_beat`/`django_celery_results`/`celery`/`redis` were removed from `INSTALLED_APPS`/`requirements.txt` entirely (they used to be listed as "installed but disabled" — they're just gone now). The cache backend is `LocMemCache` (per-process — fine for the two things it's used for, court-hierarchy caching and the tracking preview-token/rate-limit; see the `CACHES` comment in `settings.py` for the one case where this would need to become Redis-backed: running gunicorn with more than one worker process).
- **eCourts integration required first-party fixes bharat-courts doesn't ship.** The District Courts portal rejected every AJAX POST with "Invalid Request" until two things were added (`_TokenSeedingDistrictClient` in `core/services/court_data/ecourts_provider.py`): (1) a real `app_token` seeded from the `casestatus/index` page, since bharat-courts' vendored `_init_session()` GETs the tokenless home page instead; (2) a `delimeter` request header scraped live from the portal's own `components.js` — its value rotates per session/deploy, so it cannot be hardcoded. Both are application-layer checks, not a WAF/IP/TLS-fingerprint block. See the module docstring in `ecourts_provider.py` for the full reverse-engineering history (CNR search, advocate search, order downloads) if you're touching this code.
- **eCourts case tracking is rate-limited to one real fetch per case per hour**, and advocate search/import are capped to one job of each type system-wide at a time (`JobAlreadyRunningError`) — running two fan-outs against the portal concurrently caused a production outage. Don't remove either limit without understanding why it's there.
- **CORS/auth are different domains** — Vercel frontend and EC2 backend are cross-origin. Token-based auth (see Multi-tenancy above) is what's actually implemented, specifically to sidestep cross-domain cookie issues.
- `.env` is gitignored and has never been committed — keep it that way. Never put real secrets directly into `settings.py` defaults.
- **`USE_GROQ` only affects chat generation, never embeddings; `USE_GEMINI_EMBEDDINGS` only affects embeddings, never generation.** These two toggles are fully decoupled axes, and both are shared between the Case Bot chat path and the order-summary path (order-summary only ever touches the LLM axis, never embeddings). If both embedding toggles are false, embeddings fall through to Ollama's `nomic-embed-text` — Ollama must still be installed and running in that case regardless of `USE_GROQ`.
- **No production `GROQ_API_KEY` or `GEMINI_API_KEY` exists yet.** Keys used to verify these integrations were local-testing-only. Before `USE_GROQ=true` or `USE_GEMINI_EMBEDDINGS=true` can go live, generate dedicated production keys (console.groq.com/keys, aistudio.google.com/apikey) and add them to prod `.env` — do not reuse dev/test keys for production. Also see the Ollama-on-EC2 gap noted for the same deploy (Ollama isn't installed on the EC2 instance yet, and is still the embedding fallback if `USE_GEMINI_EMBEDDINGS=false`).
- **`GeminiEmbeddingService` never silently falls back to Ollama/OpenAI on failure.** A Gemini rate limit, network error, or bad API key fails the whole `DocumentProcessor.process_document()` job (caught by its top-level `except Exception` → `processing_status="failed"` → re-raise) rather than completing the document with a mix of Gemini- and Ollama-sourced vectors, which would silently corrupt retrieval since the two models' vector spaces aren't comparable.
- **OCR needs system binaries, not just pip.** `ocrmypdf` (in `requirements.txt`) requires `tesseract-ocr` and `ghostscript` installed as system packages — both are in `deploy/provision.sh`'s apt list, but a machine that only ran `pip install -r requirements.txt` cannot OCR (the worker will fail those jobs with a subprocess error). On Windows dev boxes install Tesseract (UB-Mannheim build) and Ghostscript and put both on PATH.
- **Documents don't process, order-summaries don't generate, and advocate searches never run unless the worker is running.** Uploading only enqueues a `ProcessingJob`; run `python manage.py process_jobs` locally (or ensure the `case-intel-worker` systemd service is up in production) or jobs sit at "queued" forever.
- **Cause-list PDFs are parsed by coordinate, not text order.** `pdfminer`'s plain `extract_text()` walks the Telangana HC lists column-block-wise, separating the S.No. from the case number it belongs to. Column x-offsets are detected per document (the real lists use at least three different layouts) rather than hardcoded — a fixed offset silently parses some list types as empty, which reads exactly like "none of your cases are listed today," the one wrong answer this feature must never give. See `core/services/cause_list/telangana_hc.py`'s module docstring.
- **Invoice email delivery is optional and degrades gracefully.** Sent via Resend's transactional email API through `django-anymail` (`anymail.backends.resend.EmailBackend`), not raw SMTP — `invoice_service.py` still calls `django.core.mail.EmailMessage` exactly as before, only `settings.py`'s backend selection changed. When `RESEND_API_KEY` is absent, `INVOICE_EMAIL_CONFIGURED` is `False` and `core/services/invoice_service.py`'s send path LOGS the delivery (recipient, invoice number, amount) at WARNING and returns `sent=False` instead of raising — the feature stays usable end-to-end on a box with no mail credentials, and the fee is recorded as `send_status='logged'`, never `'sent'`. See `ADMIN_EMAIL_SETUP.md` for the one-time signup steps; the `DEFAULT_FROM_EMAIL` address must be on a domain verified in the Resend dashboard for delivery beyond the account owner's own inbox.
- **`spacy` in `requirements.txt` does NOT include its language model.** `core/services/document_processor.py`'s `_get_nlp()` loads `en_core_web_sm` for sentence splitting, but spaCy models aren't distributed as regular pip packages — `pip install -r requirements.txt` alone will not fetch it. Run `python -m spacy download en_core_web_sm` once after every fresh install (local, CI, or EC2). If skipped, this doesn't hard-crash — `_get_nlp()` catches the `OSError` and silently falls back to a blank spaCy sentencizer (worse sentence boundaries, no linguistic features), so the gap can go unnoticed for a while. `.claude/commands/deploy-checks.md` documents this as a required post-`pip install` step.
- **`node_modules` in `frontend-next/` is gitignored and does not persist across fresh checkouts, containers, or `git worktree`s.** If frontend build/lint wasn't run on a given task, check this first before assuming it was skipped for another reason — see Testing above.
