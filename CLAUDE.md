# Case Intel

Legal case management platform for a solo/small-firm advocate practicing in Indian courts: case tracking (including live eCourts integration), document management with AI-generated order summaries, a general-purpose AI chat over uploaded case documents, hearing/cause-list tracking, advocate search, appearance-fee invoicing, and travel booking.

## Stack

- **Backend:** Django 5.1.11 (pinned — see Gotchas) + Django REST Framework 3.17, `core` is the only app
- **DB:** PostgreSQL with `pgvector` (RDS in production)
- **AI — two separate, unrelated pipelines, do not conflate them:**
  1. **"Case Bot" chat** (`core/services/graph/`, `core/services/ai_workflow.py`, `ChatView`) — a general-purpose RAG chat over a case's uploaded documents, live in the frontend as the "Case Bot" panel on the case detail page. LangGraph 0.6.11, lean 3-node pipeline (`hyde_expand → hybrid_search → generate_answer`), backed by `DocumentChunk` embeddings + `VectorSearchService` hybrid (pgvector cosine + tsvector keyword, RRF fusion, cross-encoder rerank — run on onnxruntime, not torch; see `core/services/reranker.py`). Persists `Conversation`/`Message`/`Citation`.
  2. **Order-summary** (`core/services/order_summary/`) — a single-order-PDF summarizer. Does **not** use LangGraph, the graph pipeline, or vector search at all: it reads `Document.extracted_text` directly, classifies the order (`routing.py`) to skip the LLM entirely for unreadable/routine/short orders, and calls `get_llm_client()` directly for a one-shot JSON summary (`prompt.py`, `service.py`). Runs exactly once per order, from the `process_jobs` worker after the order's document finishes processing — never from a view or serializer.
  - LLM (chat generation) provider is independently configurable — Groq, Ollama, or OpenAI — and is shared by **both** AI paths above via `get_llm_client()`.
  - Embedding provider is independently configurable too — Gemini (`gemini-embedding-001`, truncated to 768-dim via `output_dimensionality`), Ollama (`nomic-embed-text`, native 768-dim), or OpenAI as a fallback path. Only the chat path's ingestion pipeline (`document_processor.py`) uses embeddings; order-summary does not.
- **Court data:** `bharat-courts` wrapping the live `services.ecourts.gov.in` (District Courts) / `hcservices.ecourts.gov.in` (High Courts) portals for case tracking, order downloads, and advocate search. First-party fixes for portal bugs bharat-courts doesn't handle — see Gotchas.
- **Cause lists:** every tracked hearing in a covered court gets item number, court, bench and list type before it is heard; hearings in an uncovered court say so. Telangana HC, 17 other High Courts via hcservices (PDF parsers per layout family), and District Courts (per-court HTML lists, matched on CNR). Demand-driven, systemd-timer-driven — see Architecture and Gotchas.
- **Frontend:** `frontend-next/` — Next.js 15 / React 19 / TypeScript / Tailwind, deployed on Vercel
- **Background jobs:** a `ProcessingJob` row per unit of work (`document`, `order_sync`, `advocate_import`, `advocate_search`, `case_briefing`), claimed by the `process_jobs` worker via `select_for_update(skip_locked=True)` — **deliberately no Celery/Redis**, Postgres is the queue. See Gotchas.
- **Config:** `python-decouple`, all environment-dependent settings must be read via `config(...)` in `case_intel_project/settings.py` — never hardcode `DEBUG`, `ALLOWED_HOSTS`, `SECRET_KEY`, DB credentials, or API keys directly in source.

## Architecture

- **Models** (`core/models/`, 30 total, all registered in `core/admin.py`) — grouped by domain:
  - Case/contacts: `Case`, `ClientContact`, `CaseTag`/`CaseTagMap`, `Hearing`
  - Documents: `Document`, `DocumentVersion`, `DocumentChunk`, `DocumentTag`/`DocumentTagMap`, `Folder`
  - Case Bot chat: `Conversation`, `Message`, `Citation`
  - Court tracking/orders: `CourtFetchLog`, `CourtOrder`, `CourtTrackingPreview`, `AdvocateSearchPreference`
  - Billing/travel: `AdvocateProfile`, `AppearanceFee`, `TravelBooking`
  - Email: `Email`, `EmailAttachment`, `GmailCredential`
  - Deadlines/prep: `Task` (the one list of everything due — manual, court-order directions, limitation), `CaseBriefing` (cached hearing-prep paragraph)
  - Jobs/auth/misc: `ProcessingJob`, `ActivityLog`, `AccountLock`, `InviteToken`

  All case-data-holding models inherit an `OwnedModel` abstract mixin (`owner` FK to `User`, `on_delete=PROTECT`) for multi-tenant row isolation — see Conventions below.

- **AI service factory** — `core/services/ai_service_factory.py` has two independent toggle chains, one per axis. `get_llm_client()` checks `USE_GROQ` first (routes to `LLMClient` with Groq's OpenAI-compatible `base_url`), then `USE_OLLAMA` (`OllamaLLMClient`), then falls back to OpenAI (`LLMClient` with no `base_url` override) — untouched by `USE_GEMINI_EMBEDDINGS`. `get_embedding_service()` checks `USE_GEMINI_EMBEDDINGS` first (`GeminiEmbeddingService`), then `USE_OLLAMA` (`OllamaEmbeddingService`), then falls back to OpenAI's `EmbeddingService` — untouched by `USE_GROQ`. `GeminiEmbeddingService` always passes `output_dimensionality=settings.EMBEDDING_DIMENSIONS` (768) explicitly on every `embed_content` call and batches up to 100 texts per request (the API's per-request cap); it raises on any API error rather than falling back to another provider mid-document, since mixing embedding models within a document corrupts retrieval.
- **Document ingestion** (`core/services/document_processor.py`) — extract text (PyPDF2/python-docx/plain read) → OCR if scanned (`ocrmypdf`) → spaCy sentence-aware chunking → embed in batches of 100 → bulk-insert `DocumentChunk` rows → populate `tsvector` for keyword search. SHA-256 content-hash dedup: an identical file re-upload clones the original's chunks instead of re-embedding. This pipeline feeds **only** Case Bot retrieval; order-summary reads `Document.extracted_text` directly and never touches `DocumentChunk`.
- **eCourts integration** (`core/services/court_data/`) — `CourtDataProvider` abstraction (`base.py`) over `EcourtsProvider` (`ecourts_provider.py`, the only module that imports `bharat_courts`), with the HTML/PDF response-parsing functions split into a sibling `ecourts_parsing.py`. Public methods are synchronous; `asyncio.run()` bridges into bharat-courts' async client internally. `court_tracking.py` orchestrates the case-detail-page-facing setup/preview/confirm/refresh flow (rate-limited to one real fetch per case per hour); `court_order_sync.py` downloads order/judgment PDFs for a tracked case into the normal document pipeline (sequential, capped per sync, deduped by `CourtOrder.dedup_key`).
- **Order summaries** (`core/services/order_summary/`) — see AI section above. `routing.py` classifies order text (unreadable / too-short / routine-adjournment / needs-LLM) via a two-sided marker system: a "substantive" marker (e.g. "is directed", "shall file", "stayed") always overrides a length-based free path, since a short order can still carry a real direction.
- **Order check** (`core/services/court_order_sync.py`, `core/services/order_sync_status.py`) � every order the portal lists is saved as a `pending` `CourtOrder` (`download_status`, `download_attempts`, `last_download_error`) *before* its PDF is fetched, so a later sync finishes the same row (dedup on `dedup_key`) and never makes a second. Downloads retry only transient errors (CAPTCHA/portal/dropped connection), 5 s then 15 s; two orders failing in a row stop the sync; a row that fails 6 whole syncs becomes `failed`. The worker stores `{listed, new, downloaded, failed, pending, ...}` in `job.payload["result"]` and ends the job `partial` (not `succeeded`) when a download failed; `failed` stays for a listing that never came back. `GET /api/cases/` and `/api/cases/<id>/` carry `order_sync: {state never|queued|running|ok|partial|failed, last_checked_at, last_success_at, found, downloaded, reason}` � the latest non-cancelled `order_sync` job decides, a later success clears a failure, `reason` is one of three fixed labels, never raw error text. `document_count` counts `Document` rows only; the Cases card adds an amber marker for a tracked case whose check failed/partly worked/never ran. Interim and Final district orders carry a `section`; only `final` extends the `dedup_key` (`:final`), so every key saved earlier keeps matching. `manage.py requeue_order_sync` (dry run unless `--apply`; `--limit`, `--max-in-flight`, `--spacing`, `--min-age-hours`, `--retry-failed`) re-queues tracked cases with no downloaded order.
- **Advocate search** (`core/services/advocate_search.py`) — a state-wide **fan-out**: the eCourts "Search by Advocate" form is scoped to one court complex at a time, so this runs the search sequentially across every district/complex in a state (dozens to hundreds of CAPTCHA-gated portal calls, ~10–45 minutes depending on state size), aggregating and deduping results by CNR. Runs only inside the `process_jobs` worker, never inline. Per-district and per-complex failure isolation (one bad complex doesn't abort the run); progress and partial results are persisted to `job.payload` incrementally after every district so a crashed worker doesn't lose completed work, and a separate "retry failed districts" job can re-run just the gaps. **Concurrency cap:** only one `advocate_search` and, separately, only one `advocate_import` job may be in flight system-wide at a time (`JobAlreadyRunningError`) — running two fan-outs at once against the portal caused a production outage. **Every result is verified against the searched name** (`parse_advocate_search_html` in `ecourts_parsing.py`, scored with the same `name_matching.name_similarity` the conflict check uses): rows whose court-recorded advocate shares no real name token are dropped, and rows that can't be checked (no Advocate column, blank cell, or any bar-code search) are kept but flagged `advocate_match_verified: false` — the results table shows them as "Not verified" and never as a match.
- **Cause lists** (`core/services/causelists/`, docs in `docs/causelists/`) — an **adapter framework**: `registry.resolve_case(case)` decides, with no network, which adapter/listing target covers a case (`telangana_hc`; `hcservices_generic` for the other High Courts, data-driven by `hc_config.py`; `district_ecourts`; `supreme_court` is built and tested but **dormant**: no Supreme Court case can exist in the DB) or that none does → hearing state `unsupported` ("Not covered"). `service.run()` is demand-driven: it takes the scheduled hearings of the next IST days, groups them by (adapter, target, date), fetches ONLY those lists (one fetch shared by everyone in the same court), parses each document page by page from a temp file, matches (CNR first, then `normalize.canonical_case_key`), and is the **only writer** of `Hearing.cause_list_*`. **The rule everything serves: a hearing becomes `not_listed` only when every document the court's own index lists for that target and date was fetched and parsed** (`service.decide_outcome` is the single place that assigns it; a test greps for any other). Anything less is `not_published` (documents not uploaded yet / no list yet), `fetch_failed` ("Couldn't check": CAPTCHA, timeout, unreadable document, budget) or `unsupported`; `listed` is never overwritten by a failure. Matches (all of them, primary first) are stored in `CauseListMatch` (owned); `CauseListFetch` is the public-metadata ledger (not owned, no API). Each parser also reconciles itself against an independent count and raises rather than return a partial list. District courts: one judge per CAPTCHA request, civil and criminal separately, located via `Case.court_locator` (filled by the case-refresh flow from the CNR page, or `manage.py backfill_court_locators`). All dates are IST (`causelists/clock.py`), whatever the box clock. Locks (`causelists/lock.py`): one run at a time (advisory lock); nothing runs while an advocate search/import is running; the District/hcservices adapters also wait for a tracked-case refresh; sci.gov.in needs no lock. `manage.py fetch_cause_lists [--court all|<adapter>] [--check|--dry-run]`, `manage.py causelist_doctor --adapter X --target Y --date D` (fetch+parse+match, writes nothing). Settings: `CAUSE_LIST_ADAPTERS` and the `CAUSE_LIST_*` budgets in `settings.py`.
- **Invoicing** (`core/services/invoice_service.py`) — `AppearanceFee` is one billable charge on a hearing; a hearing can carry several (`hearing` is a ForeignKey, `related_name="appearance_fees"`), each with a `category` (`appearance`/`hotel`/`flight`/`other`), its own invoice number and its own lifecycle. Only `appearance` falls back to `AdvocateProfile.default_fee_amount` on create; every other category needs an explicit amount. Lifecycle is `PENDING → INVOICED → PAID`, enforced by this module (views never assign `fee.status` directly). Per-advocate invoice numbering via `select_for_update()` on `AdvocateProfile` so concurrent generates from the same advocate serialize correctly. PDF rendering via `fpdf2` (pure Python, no system deps, unlike WeasyPrint). Email delivery is optional — see `INVOICE_EMAIL_CONFIGURED` in Gotchas.
- **Tasks & deadlines** (`core/services/tasks/`, `core/models/task.py`) — `Task` is the single deadline surface: `kind` is `manual`, `order_direction` or `limitation`. System code creates tasks only through `upsert_system_task()` (idempotent on a per-owner `dedup_key`; never touches a task the advocate edited, completed or dismissed). Order-direction tasks are generated in the worker right after an order is summarised (`from_orders.py`: your side's directions only, party role must be known, latest recent order only; due dates from a regex table in `direction_deadlines.py`, not an LLM) and re-synced when `user_party_role` changes; `manage.py generate_order_tasks` backfills. Limitation deadlines (`core/services/limitation/`) come from a reviewed rules table in code (`rules.py`) and a conservative computation (`compute.py`: earliest possible date; Section 12(2)/4/5 caveats stated as notes, not applied) — added by the advocate, never auto-triggered yet. `/api/tasks/` lists them; a system task can be dismissed but not deleted.
- **Hearing prep sheet** (`core/services/hearing_digest/`) — per-hearing composition (cause-list slot, last order via `build_order_summary`, open tasks, documents) plus one cached LLM "state of the matter" paragraph (`CaseBriefing`), generated on demand by a `case_briefing` job via `get_llm_client()` — NOT the Case Bot graph. The cache is keyed on a fingerprint of the facts; the prose names petitioner/respondent so a party-role correction needs no regeneration. PDF via fpdf2 (`pdf.py`, shared `core/services/pdf_utils.pdf_safe`).
- **Conflict check at intake** (`core/services/conflict_check.py`, `core/services/name_matching.py`) — a new matter's parties are compared with the advocate's own cases (never another tenant's) for the same party on opposite sides. Token-alignment scoring (no fuzzy-match dependency, no `pg_trgm`), State/police parties stoplisted, labelled fixture in `core/tests/fixtures/party_names.json`. Warns, never hard-blocks: `POST /api/cases/` and `cases/cnr-lookup/create/` answer 409 `code: "conflict_check"` until `acknowledge_conflicts` is sent (logged to `ActivityLog`); the import worker records hits in `job.payload["conflicts"]`. Needs `Case.petitioner_name`/`respondent_name` (set on every fetch; `manage.py backfill_party_names` fills older cases from stored search results, no portal calls). `manage.py conflict_check_report --owner <u>` is a read-only tuning aid.
- **Background processing** — `ProcessingJob.job_type` is one of `document`, `order_sync`, `advocate_import`, `advocate_search`, `case_briefing`; the `manage.py process_jobs` worker (systemd unit `case-intel-worker` in production, see `deploy/case-intel-worker.service`) claims jobs via `select_for_update(skip_locked=True)`. `updated_at` doubles as a heartbeat — a `running` job whose heartbeat has gone stale is reclaimed (crashed-worker recovery). Scanned PDFs (negligible extractable text) are OCRed with `ocrmypdf --skip-text` in 10-page batches inside the worker (`core/services/ocr_service.py`), setting `Document.ocr_applied`. Claims are **priority-ordered, not FIFO** (`_job_priority` in `process_jobs.py`): a user's own upload/briefing, then background-fetched `court_order` document jobs, then the long portal jobs (order sync, refresh-all, advocate import/search). That only reorders what is waiting — it cannot interrupt a running job — so `--lane interactive` lets a second worker serve uploads while the first is inside a 10–45 min fan-out. The default `--lane all` is unchanged.
- **Views/serializers** — `core/views/`, `core/serializers/`, both modular packages split by domain (case, hearing, document, chat, conversation, folder, gmail, email, court_order, case_tracking, advocate_search, advocate_profile, appearance_fee, travel_booking, client_contact, auth, dashboard).
- **URLs** — `core/urls.py`, all endpoints mounted under `/api/`.
- **Multi-tenancy** — `core/views/mixins.py`'s `OwnerScopedMixin` is applied to every generic view; it filters `get_queryset()` by `request.user` and stamps `owner` on create, which also covers object-level retrieve/update/delete since DRF's `get_object()` reuses `get_queryset()`. Plain `APIView`s (dashboard, chat, gmail, case_tracking, advocate_search, appearance_fee, travel_booking, document upload/process/download) are scoped manually — check each one individually rather than assuming the mixin covers it. Serializers with writable FKs to owned objects (`Hearing.case`, `Document.folder`, `Folder.parent_folder`) scope those PK querysets to the caller's own rows too.
  - **Case Bot retrieval is owner-scoped inside the pipeline, not just at the view.** `VectorSearchService.search()` takes a **required** `owner_id` (keyword-only, no default) and filters every retrieval leg (vector + keyword) by `DocumentChunk.owner`; `case_id` only narrows *within* the owner's rows and never substitutes for the owner filter. `owner_id` is threaded `ChatView → AIWorkflowService.process_query (owner_id = user.id) → AgentState["owner_id"] → hybrid_search node`, and `hybrid_search` raises rather than run unscoped if it's missing. HyDE/rerank/citation-extraction/`build_ai_context` never touch chunks outside this scoped path.
- **Auth** — DRF `TokenAuthentication`. Frontend sends `Authorization: Token <token>`, stored in `localStorage`. Chosen over session/JWT because Vercel↔EC2 is cross-origin with `CORS_ALLOW_CREDENTIALS=False`, so cookies don't work here regardless.

## Testing

`pytest` + `pytest-django` (`pytest.ini` at repo root), ~680 tests. **DB tests need a local Postgres with pgvector**: pass `DB_HOST=localhost` (plus local `DB_USER`/`DB_PASSWORD`/`DB_NAME`) as environment variables, which python-decouple reads ahead of `.env`. A root `conftest.py` refuses to build the test database on any non-local host (override: `ALLOW_REMOTE_TEST_DB=1`), because a `.env` copied from the server points at production RDS and pytest-django would CREATE/DROP a database there. `TestEndpointTenancyCoverage` in `test_multi_tenancy.py` fails if a routed view neither uses `OwnerScopedMixin` nor is listed as reviewed — add new plain `APIView`s to its lists deliberately. `core/tests/test_multi_tenancy.py` covers cross-user isolation on Case/Hearing/Document/Conversation export, the register/login/logout flow, and **Case Bot retrieval isolation** (`TestCaseBotRetrievalIsolation` — `POST /api/chat/` with and without `case_id` must never retrieve or cite another tenant's `DocumentChunk`) — extend it as new owned models/endpoints are added, don't let it stay a one-off. Other suites worth knowing about: `test_advocate_search.py` (the state-wide fan-out, including the concurrency cap and per-district retry), `test_advocate_search_verification.py` (result verification against the real 5-column grid; fixtures deliberately use party names unrelated to the searched advocate, so a regression can't accidentally look validated), `test_cause_list.py` (uses real captured fixtures under `core/tests/fixtures/causelists/`, not synthetic HTML; `TestScheduledFetchCommand` covers the `fetch_cause_lists` court registry + `--check` preflight the systemd timer depends on), `test_order_summary.py` (routing/no-LLM paths, JSON retry, party-aware rendering), `test_court_orders.py`, `test_tracking_refresh_regression.py`, `test_tasks.py`, `test_order_directions.py`, `test_hearing_digest.py`, `test_conflict_check.py`, `test_limitation.py` (the rules table's periods are pinned — changing one is a reviewed diff).

**Frontend verification is not optional when `frontend-next/` files change.** Run `npm install && npm run build && npm run lint` from `frontend-next/` and actually read the output — don't report a task as tested if this step was skipped because `node_modules` was missing.

## Workflow conventions for AI-assisted changes (Claude Code)

- **Never run `git commit` or `git push`.** Leave changes uncommitted in the working tree for manual review and commit.
- **Never touch deployment configs**: systemd units, nginx conf, GitHub Actions, `.env` files. Flag needed changes in your summary instead.
- **Every model holding user/case data must have an `owner` FK** (via `OwnedModel`) and **every queryset must filter by `request.user`** — either through `OwnerScopedMixin` or manual scoping on plain `APIView`s. Check writable serializer FKs too (see Multi-tenancy above) — an unscoped PK field is an IDOR path even if the view itself is scoped.
- **Migrations**: never edit an applied migration; always `makemigrations` fresh. For migrations adding a NOT NULL column to a table with real production rows, use the `CHECK ... NOT VALID → VALIDATE → SET NOT NULL` pattern and `CREATE INDEX CONCURRENTLY` rather than a bare apply, to avoid an `ACCESS EXCLUSIVE` lock on RDS during business hours.
- **Django is pinned to 5.1.11 — do not upgrade it** (see Gotchas) as part of unrelated work; if a task seems to require a newer Django, stop and flag it rather than bumping the pin.
- **The Case Bot chat pipeline and the order-summary pipeline are separate systems that happen to share an LLM client factory.** Don't assume a change to one affects the other, and don't route order-summary work through LangGraph (or vice versa) without a deliberate decision to merge them — they were built independently and currently have no shared code path beyond `get_llm_client()`.

## Gotchas

- **A DRF `format` query parameter never reaches the view.** DRF treats `?format=` as a renderer override (`URL_FORMAT_OVERRIDE`), and with only `JSONRenderer` configured, `?format=pdf` returns 404 from content negotiation before auth or the view runs. Use a separate path (e.g. `hearings/<id>/digest/pdf/`). `conversations/<id>/export/?format=` is affected by exactly this.
- **`next build` does not type-check** (`typescript.ignoreBuildErrors: true` in `frontend-next/next.config.mjs`). Run `npx tsc --noEmit` separately; it currently reports pre-existing errors in the emails/Gmail/document-dialog/hearings-hook files.
- **The advocate-search results grid is its own layout — never parse it with bharat-courts' `parse_case_status_html`.** `casestatus/submitAdvName` returns `Sr No | Case Number | Parties | Advocate Name | View`; the vendored parser's >4-column branch reads fixed offsets built for a different grid and silently discards the Advocate column, which is how unrelated cases once reached users looking like matches. The portal itself *does* filter by name server-side (verified live 17 Sep 2026: a nonsense name returned 0 rows), but its matching is loose — a search for "Ramesh Kumar" also returns `APP G.Ramesh kumar`, a government prosecutor, and `B. Ramesh Kumar`. Name matching cannot tell two real people with the same name apart, so matched rows carry `matched_advocate_text` and the UI shows it for a human to judge; don't "fix" that by hiding it. The Advocate column is found by header text, not column index, because eCourts layouts vary across complexes/states. `_extract_cnr`/`_extract_parties` are deliberately imported from bharat-courts' private parser (same posture as `_TokenSeedingDistrictClient`).

- **Outbound calls in a web request are all bounded — keep it that way.** gunicorn `gthread` (and, before it, sync workers) has no per-request kill that works for a stuck provider call, so every outbound call carries its own limit: LLM (`LLM_REQUEST_TIMEOUT_SECONDS`/`LLM_MAX_RETRIES`, HyDE gets a single `AI_HYDE_TIMEOUT_SECONDS` attempt), the Gemini *query* embedding (`GeminiEmbeddingService.QUERY_TIMEOUT_SECONDS`, ingestion keeps its patient retries), and eCourts case/CNR/hierarchy lookups (`COURT_PORTAL_CALL_TIMEOUT_SECONDS` via `_run_bounded`). Worst case for one Case Bot request is HyDE (10 s) + answer (25 s x 2 attempts) + embedding (8 s x 2) = 76 s plus SDK back-off at the defaults; a test (`test_llm_timeouts.py`) pins it under the 120 s gunicorn timeout.
- **The Case Bot reranker must not pull torch into the web process.** `RERANKER_BACKEND=onnx` (default) runs the model's published ONNX export (pinned revision in `reranker.py`) on onnxruntime + `tokenizers`: +~116 MB per worker versus +~430 MB for sentence-transformers/torch, same scores to ~1e-5 and identical rankings (`test_reranker.py` re-checks when the model is cached). Scores are raw logits and `graph/nodes.py` compares the top one to `CONFIDENCE_THRESHOLD`, so `RERANKER_BACKEND=none` (plain RRF scores ~0.02) makes *every* answer carry the low-confidence note — it is an emergency switch, not a free saving. A failed reranker load is logged at ERROR and retried after `RERANKER_RETRY_SECONDS`, never cached forever. `torch`/`transformers`/`sentence-transformers` are only needed for `RERANKER_BACKEND=torch` and the parity test.
- **Django is pinned to 5.1.11** — do not upgrade. A newer Django version conflicts with dependencies as installed here. Check `requirements.txt` compatibility before ever touching this pin.
- **`DEBUG` / `ALLOWED_HOSTS` / `SECRET_KEY` must come from `.env` via `python-decouple`**, not be hardcoded. (`SECRET_KEY` was hardcoded in source until this was fixed — if you see a hardcoded fallback default in `settings.py`, that's intentional for local-dev-without-`.env` convenience, not a place to put real secrets.)
- **Embedding dimensions are NOT fully dynamic.** `settings.py` computes `EMBEDDING_DIMENSIONS` dynamically based on `USE_GEMINI_EMBEDDINGS` / `USE_OLLAMA` + the configured model (768 hardcoded for Gemini regardless of `GEMINI_EMBEDDING_MODEL`'s native dimension, 768 for Ollama `nomic-embed-text`, 1536 for OpenAI `text-embedding-3-small`), but `core/models/document_chunk.py`'s `DocumentChunk.embedding` field is **hardcoded** to `VectorField(dimensions=768)`. If you switch to OpenAI's embedder (1536-dim, no `output_dimensionality` truncation applied), embedding writes will fail or silently mismatch against the fixed 768-dim column/HNSW index. A real migration (changing the field + re-embedding existing chunks) is required to actually switch to a non-768 provider in a running deployment — flipping the env var alone is not sufficient. Gemini and Ollama are both safe to switch between since both are pinned to 768 already.
- **No Celery, no Redis — Postgres is the only queue, and this is deliberate, not a TODO.** Verified: zero `.delay(`/`.apply_async(`/`@shared_task` calls anywhere in the codebase. `django_celery_beat`/`django_celery_results`/`celery`/`redis` were removed from `INSTALLED_APPS`/`requirements.txt` entirely (they used to be listed as "installed but disabled" — they're just gone now). The cache backend is `LocMemCache` (per-process — fine for the two things it's used for, court-hierarchy caching and the tracking preview-token/rate-limit; see the `CACHES` comment in `settings.py` for the one case where this would need to become Redis-backed: running gunicorn with more than one worker process).
- **eCourts integration required first-party fixes bharat-courts doesn't ship.** The District Courts portal rejected every AJAX POST with "Invalid Request" until two things were added (`_TokenSeedingDistrictClient` in `core/services/court_data/ecourts_provider.py`): (1) a real `app_token` seeded from the `casestatus/index` page, since bharat-courts' vendored `_init_session()` GETs the tokenless home page instead; (2) a `delimeter` request header scraped live from the portal's own `components.js` — its value rotates per session/deploy, so it cannot be hardcoded. Both are application-layer checks, not a WAF/IP/TLS-fingerprint block. See the module docstring in `ecourts_provider.py` for the full reverse-engineering history (CNR search, advocate search, order downloads) if you're touching this code.
- **eCourts case tracking is rate-limited to one real fetch per case per hour**, and advocate search/import are capped to one job of each type system-wide at a time (`JobAlreadyRunningError`) — running two fan-outs against the portal concurrently caused a production outage. Don't remove either limit without understanding why it's there.
- **CORS/auth are different domains** — Vercel frontend and EC2 backend are cross-origin. Token-based auth (see Multi-tenancy above) is what's actually implemented, specifically to sidestep cross-domain cookie issues.
- `.env` is gitignored and has never been committed — keep it that way. Never put real secrets directly into `settings.py` defaults.
- **`USE_GROQ` only affects chat generation, never embeddings; `USE_GEMINI_EMBEDDINGS` only affects embeddings, never generation.** These two toggles are fully decoupled axes, and both are shared between the Case Bot chat path and the order-summary path (order-summary only ever touches the LLM axis, never embeddings). If both embedding toggles are false, embeddings fall through to Ollama's `nomic-embed-text` — Ollama must still be installed and running in that case regardless of `USE_GROQ`.
- **No production `GROQ_API_KEY` or `GEMINI_API_KEY` exists yet.** Keys used to verify these integrations were local-testing-only. Before `USE_GROQ=true` or `USE_GEMINI_EMBEDDINGS=true` can go live, generate dedicated production keys (console.groq.com/keys, aistudio.google.com/apikey) and add them to prod `.env` — do not reuse dev/test keys for production. Also see the Ollama-on-EC2 gap noted for the same deploy (Ollama isn't installed on the EC2 instance yet, and is still the embedding fallback if `USE_GEMINI_EMBEDDINGS=false`).
- **`GeminiEmbeddingService` never silently falls back to Ollama/OpenAI on failure.** A Gemini rate limit, network error, or bad API key fails the whole `DocumentProcessor.process_document()` job (caught by its top-level `except Exception` → `processing_status="failed"` → re-raise) rather than completing the document with a mix of Gemini- and Ollama-sourced vectors, which would silently corrupt retrieval since the two models' vector spaces aren't comparable.
- **OCR needs system binaries, not just pip.** `ocrmypdf` (in `requirements.txt`) requires `tesseract-ocr` and `ghostscript` installed as system packages — both are in `deploy/provision.sh`'s apt list, but a machine that only ran `pip install -r requirements.txt` cannot OCR (the worker will fail those jobs with a subprocess error). On Windows dev boxes install Tesseract (UB-Mannheim build) and Ghostscript and put both on PATH.
- **Documents don't process, order-summaries don't generate, and advocate searches never run unless the worker is running.** Uploading only enqueues a `ProcessingJob`; run `python manage.py process_jobs` locally (or ensure the `case-intel-worker` systemd service is up in production) or jobs sit at "queued" forever.
- **The district order parser has seen one real page.** `_parse_district_orders` is verified on the captured `TSHC010030082026` page (an Interim Orders table) and on one live download in production; Final Orders markup and other courts' variants are unverified. It now logs a WARNING (CNR and counts only) instead of returning `[]` silently when an orders section exists but nothing parses � grep the worker log for "found an orders section but parsed 0 orders". Zero orders listed is also the normal answer for most district cases (80 of 81 production syncs), so "No orders found on the court portal" is not by itself a bug.
- **The `core` logger does not propagate** (`LOGGING` in settings), so pytest's `caplog` never sees `core.*` records; attach a handler to the logger in the test (see `test_district_order_parsing.py`).
- **Cause-list PDFs are parsed by coordinate, not text order.** `pdfminer`'s plain `extract_text()` walks these lists column-block-wise, separating the item number from the case number it belongs to. Column x-offsets are detected per document rather than hardcoded — a fixed offset silently parses some layouts as empty, which reads exactly like "none of your cases are listed today," the one wrong answer this feature must never give. Layout families: Telangana/Andhra (`adapters/telangana_hc.py`), the common item+case table (`layouts/table.py`), Delhi's hard-wrapped cells (`layouts/delhi.py`). **Portal facts that bit before** (details in `docs/causelists/COVERAGE.md`): hcservices answers a CAPTCHA failure with plain `Invalid Captcha` or `{"Error":"ERROR_VAL"}` (empty CAPTCHA) — never "no list" (that is `No cause List Available…`); an index row can point at a PDF the court has not uploaded (body `Order not uploaded`, indistinguishable from a session-less request), and hcservices PDF links are session-bound so they can never be shown to a user; bharat-courts' `DistrictCourtClient.cause_list()` reads the wrong JSON key (`case_data` is right) and returns `[]` for every court — do not use it. Eight High Courts' lists are not served by hcservices at all (Allahabad, Gujarat, Himachal, Jharkhand, Kerala, MP, P&H, Madras-Madurai) and resolve to `unsupported`.
- **Invoice email delivery is optional and degrades gracefully.** Sent via Resend's transactional email API through `django-anymail` (`anymail.backends.resend.EmailBackend`), not raw SMTP — `invoice_service.py` still calls `django.core.mail.EmailMessage` exactly as before, only `settings.py`'s backend selection changed. When `RESEND_API_KEY` is absent, `INVOICE_EMAIL_CONFIGURED` is `False` and `core/services/invoice_service.py`'s send path LOGS the delivery (recipient, invoice number, amount) at WARNING and returns `sent=False` instead of raising — the feature stays usable end-to-end on a box with no mail credentials, and the fee is recorded as `send_status='logged'`, never `'sent'`. See `ADMIN_EMAIL_SETUP.md` for the one-time signup steps; the `DEFAULT_FROM_EMAIL` address must be on a domain verified in the Resend dashboard for delivery beyond the account owner's own inbox.
- **`spacy` in `requirements.txt` does NOT include its language model.** `core/services/document_processor.py`'s `_get_nlp()` loads `en_core_web_sm` for sentence splitting, but spaCy models aren't distributed as regular pip packages — `pip install -r requirements.txt` alone will not fetch it. Run `python -m spacy download en_core_web_sm` once after every fresh install (local, CI, or EC2). If skipped, this doesn't hard-crash — `_get_nlp()` catches the `OSError` and silently falls back to a blank spaCy sentencizer (worse sentence boundaries, no linguistic features), so the gap can go unnoticed for a while. `.claude/commands/deploy-checks.md` documents this as a required post-`pip install` step.
- **`node_modules` in `frontend-next/` is gitignored and does not persist across fresh checkouts, containers, or `git worktree`s.** If frontend build/lint wasn't run on a given task, check this first before assuming it was skipped for another reason — see Testing above.
