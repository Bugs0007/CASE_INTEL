Decision aid, not a spec

What Case Intel builds next

Case Intel already carries a matter from advocate-name search through eCourts tracking, Telangana HC cause lists, order sync with AI overviews, and appearance-fee invoicing. This console weighs the candidates for what comes after, against one test: how much of the existing machinery a feature reuses, set against how much a solo litigator would actually feel it.

LeverageHow much of what is already built (services, worker, LLM factory, eCourts layer, RAG pipeline) the feature reuses rather than adds.
ValueHow directly a solo or small-firm advocate practising in Indian courts would feel it, week to week.
New infraThe size of what has to be built from nothing: a new model, a new integration, a new parser family.
Scoreleverage × value − new infra. Tier order follows it. Effort is sized S / M / L, not broken into tasks.

Where the product stands

Every claim below was checked against the code, not the docs. Three states: shipped and working, built but switched off, and absent.

Shipped working in production

  • Advocate-name / bar-code search, state-wide fan-out, bulk import
  • eCourts case tracking, CNR auto-detect across District + High Court
  • Hearing history with per-hearing purpose
  • Telangana HC cause lists (coordinate-parsed PDFs, 4 hearing states)
  • Court-order sync + AI Order Overview with party-attributed directions
  • Appearance-fee invoicing: PENDING → INVOICED → PAID, numbered PDF, Resend email
  • Case Bot: hybrid RAG (pgvector + tsvector + RRF + cross-encoder)
  • Calendar (month + by-court), dashboard "needs attention"

Dormant built, not wired

  • Gmail sync: models, gmail_service.py, views all exist; GMAIL_INTEGRATION_ENABLED = false, OAuth callback unfinished, hidden from nav
  • Citation.email FK exists; nothing ingests email text into the chunk store
  • Task and DocumentVersion models: admin-registered, zero code paths
  • Cause-list fetch: idempotent command, but no scheduler; depends on the operator adding two cron lines

Absent no code at all

  • Limitation / deadline calculation of any kind
  • Conflict checking at intake
  • Client-facing communication (email or WhatsApp updates)
  • Document drafting or assembly
  • Cause lists beyond Telangana HC (no SCI, no District, no other HC)
  • Supreme Court support: ESCR CNR prefix is dropped, no supreme_court court_type
  • Time tracking, trust / retainer ledger, recurring invoices
Tier 0 / fix, not feature

Two things that should not wait for a roadmap slot

  • Cross-tenant Case Bot retrieval. When POST /api/chat/ is called with no case_id, VectorSearchService applies no owner filter. Retrieval then spans every DocumentChunk row across all tenants, and the answer can quote another advocate's documents. DocumentChunk carries owner; the search path never uses it.
  • A real cause-list scheduler. manage.py fetch_cause_lists runs only if an operator hand-adds two cron lines. Any cause-list expansion multiplies that gap. A systemd timer or a cron-type ProcessingJob should land before, or with, the first new court.

How far cause lists can be pushed

Today: Telangana High Court only, one Principal Bench at Hyderabad. One CAPTCHA-gated POST showCauseList with flag=civ_t returns an HTML meta-table of about 58 per-judge PDFs; each PDF is parsed by character coordinate, not text order, with column offsets detected per document because the real lists ship at least three layouts.

The fetch is reusable; the parser is not. core/services/cause_list/__init__.py says it plainly: a second court means "a sibling module with its own fetcher and parser", not a generalisation of this one.

›Why this is a non-target, and what to read it as instead

The "benches" in the meta-table are judge combinations, not seats. Telangana High Court sits only at Hyderabad, so one POST with court_code=1 pulls the whole court. There is nothing to add here.

Read the request as Telangana District Courts instead (row below): that is the adjacent surface, and it is where the advocate-search import users actually practise.

›Self-contained, no CAPTCHA, and it closes half the ESCR gap

The SCI serves daily lists as static PDFs on a dated path. No token seeding, no CAPTCHA on the download, about 15 to 20 court PDFs a day against Telangana HC's 58. bharat_courts.SCIClient has no cause-list method and its case searches raise NotImplementedError, so this is first-party, but it is a small, bounded first-party job.

SCI lists carry the Advocate-on-Record name in a column, which is a stronger match key than a bare case number. The parser is new but the SCI layout is more stable than the HC template zoo.

›Where the import users actually are, and the two real obstacles

The hardest part, the District portal session (real app_token, rotating delimeter value, rotating second-header key, session cookie), is already built and reverified live. The cause-list call rides on top of it.

Obstacle 1
Matching. District cases carry portal codes like "2^2" that normalize_case_token deliberately rejects. Cause-list matching for District would key on the case type / number / year already stored in tracking_config, not the printed token. A new code path, parallel to the HC one.
Obstacle 2
Scope. There is no state-wide District cause list. You fetch per establishment, per court number. The tractable version only pulls lists for the establishments where the advocate has a hearing that day, driven off tracked Hearing rows.
State to add
The current tracked_hearings_on() is scoped court_type="high_court". District needs its own scope and matcher.

›The path to national coverage, and why it stays expensive

This is what Provakil sells: SC, every HC, every District court, consumer forums, the tribunals. Each High Court's cause list is its own PDF layout, and several HCs sit at multiple benches so the single-submit shortcut does not hold. The fetch generalises; every parser is new.

Sequencing: pick HCs by where the user base actually files. There is no leverage shortcut across courts, only a repeatable process (fetch, capture real fixtures, write the coordinate parser, verify it never returns a silent empty).

›Fully closes the named gap, lowest audience per unit of effort

Right now _guess_court_type_from_cnr recognises an ESCR prefix through bharat_courts.infer_court_from_cnr, then explicitly returns None ("this app has no Supreme Court support"). _fetch_by_cnr_auto only ever tries ("district", "high_court"), so a genuine SC CNR is queried against both portals and returned as "not found in either".

Closing it means: the CAPTCHA-gated case-status form (its own reverse-engineering spike), a new provider branch, a supreme_court value threaded through VALID_COURT_TYPES, the models, the views and the frontend validation. Worth it if SC matters become common in the user base; today they are rare for a District/HC advocate.

Order within cause-list work: SCI cause lists and Telangana District together (one self-contained, one on the real user base), then AP HC (cheap proof), then other HCs (expensive, national), then SCI case tracking (completes the gap, niche here). All of it sits behind the Tier-0 scheduler.

Manual work the existing infrastructure could absorb

The reusable parts: the ProcessingJob Postgres worker, get_llm_client() (Groq / Ollama / OpenAI), the document pipeline, the eCourts provider, the order-summary marker system, fpdf2, the Resend send path, and the hybrid RAG store. Each card names what it reuses and the manual task it replaces.

Where the product sits

The US-market leaders do not touch Indian courts. The real comparison set is Provakil and the newer Indian advocate apps. The eCourts-native integration is a genuine differentiator; it is also the only one that is hard to copy.

What Case Intel has that the field does not

  • eCourts-native scraping integration. A real moat against Clio, MyCase, PracticePanther and Filevine, none of which track Indian courts. The first-party work (token seeding, rotating anti-scrape headers, CNR auto-detect across District and HC, CAPTCHA OCR) is hard and, outside Provakil, largely un-replicated.
  • CNR auto-detection. Prefix to court type, auto-tries both portals. Smoother than the portal-code cascade the other tools expose.
  • AI Order Overview with the routing / marker system. Skips the LLM entirely for routine adjournments; extracts directions attributed to petitioner vs respondent. More considered than "summarise this PDF".
  • Advocate-search fan-out with transparent per-district retry and resume. Bootstraps a whole practice's case list from a bar code.
  • Coordinate-based cause-list parsing that refuses a silent empty. "None of your cases are listed" must never be a parser bug; the code enforces that.
  • Hybrid RAG and a self-hostable AI path. pgvector + tsvector + RRF + cross-encoder, with an Ollama option and no per-seat SaaS lock-in.
